# Plan and status

Updated 2026-11-15 (after the review of the layout fixes and the fairy's effects, row 34; a skipped scene over at once, row 35; the fairy's close-up, row 36; a skip without the black screen, row 39). For the architecture and how to continue, read [`docs/LLM_GUIDE.md`](docs/LLM_GUIDE.md).

## Architecture decision

`RcHcGame.dat` is recompiled statically from x86 to WebAssembly and runs as shipped. A JavaScript host gives it the Windows services it asks for. Three things are not the original code:

1. **The render driver.** Genesis3D talks to its display through a driver DLL with one export, `DriverHook`. The host answers `LoadLibrary(".\D3DDrv.dll")` itself and implements that driver table (`source/host/gdriver.js`), following the behaviour of the original `D3DDrv.dll` as recovered in `docs/research/genesis-driver.md`. No DirectDraw or Direct3D is emulated.
2. **The top of the main loop.** `CAdamApplication::MainLoop` (0x4BFD60) is run by the host with the same calls (`source/host/mainloop.js`), so that the whole game can be saved between two passes.
3. **The menu and launcher** (`RcHcMenu.dat`, `RedCat.exe`) are not recompiled. The menu is the HTML reconstruction from the JavaScript port (`source/menu/`, `docs/menu.md`); the page writes the INI values the original menu and launcher would leave behind (`source/host/ini.js`) and starts the game with `-game`.

The game thread is a worker that stays inside the original `WinMain`. The original nested loops (in-game menu, pause, results, loading) spin on rendering and `PeekMessage`, so the worker never returns to its event loop: input comes through shared memory, and each frame's render calls go as one message to a render worker that owns the page's canvas (no picture can leave a thread that never returns to its event loop without leaking, see `docs/LLM_GUIDE.md`).

## Open decisions

- **Games saved before 2026-11-14 stay "Low End PC"**, a state the original only had after choosing Laag or Normaal (its default is 2), which weighs for doing something about it. The switch is in the game's memory and so in a save state: a player who continues such a state keeps the fairy without her effects, through changes of world too, until he starts a world from the menu without continuing ("<wereld> opnieuw beginnen", a Snelspel, a new adventure). Options: leave it (it wears out as players start worlds); drop the old states once (`STATE_ABI`), which costs every player his saved place; or switch a restored game at its next change of world, which was not tried: the fairy's orbiters are set up when a level loads (0x478A00) and every object's range in its constructor, so the moment must be before a level's objects are made, and such a game would no longer continue bit for bit.
- **Larger far shots.** The owner's own addition to the JavaScript port; he left it out when he asked for the hand torches (2026-11-14). Not researched: where `CRcWeaponProjectile` and the enemies' shot classes hand their sprite and its scale to the engine, and whether that scale also feeds collision.
- **Torch light on walls** is about twice as strong as in the JavaScript port with the same colour and radius (Castle wall +12..21 % against the port's +6..9 %; `docs/research/original-fixes.md` 10, pictures `tools/out/torches/review-fidelity/diff-sheet.png`). Left as the engine computes it. For the port's subtler look: lower `LIGHT.rgba` or `radius` in `source/host/torches.js` after a side-by-side. Likewise the number of lights: eight torches on top of the game's own, the port at most seven sharing eight slots.

## Known gaps

- Skipping a scene: the key is E for everybody (setting `keys.skip`, not in the form Toetsen instellen); a player who gave E to an action of the game still skips with it. The two levels' script variables (Graveyard `paal1`…`paal5`, Tower `HasLastMirror`, `MirrorsPlaced`) were not part of the comparison. What the original makes depend on the frame rate (random waiting times, where a wandering enemy is, whether an enemy has noticed RedCat: the Forest's Brutus has not after a skip, as on a machine that draws 30 frames a second) can differ after a skip from what a watched scene at 60 frames a second leaves, as it differs between two machines; a skip is the game at two passes a second, the slowest rate at which the original loses no game time. The tail of a skip notices a hit or another scene up to half a second of game time late. Input during a skip is dropped, so a key held through it must be pressed again. `Say` messages outside scenes have no box.
- Full screen: a visitor who stored settings before 2026-11-14 keeps the `false` that was stored with them. A dialog of the port open over a full-screen game and closed with Esc may leave full screen as well (the browser's choice), and the game then gets an Esc: not tried.
- Keys: the form in the main menu cannot be opened over a running game (the game's own Spelbesturing is there), offers one key per action although the file may hold more, and does not list the game's other actions (Menu, Pauze, fly up and down, scores). A player whose file was changed before and still has the original's `Walk=Alt` next to a Shift that is taken has no key for walking slowly until he sets one (Alt is not watched while it is the sidesteps' key). The walk animation does not slow down with a slow walk.
- Controller: in the game's own menus the left stick only moves up and down (the d-pad does all four); no button for saving or loading. A d-pad direction also presses the arrow key, so a player who binds an arrow to something else gets that too.
- The screen's shape and field of view: cutscene cameras that set their own field of view were not checked. The field of view setting is fixed when a game starts; the screen's shape follows the window, but not while one of the game's own loops is on screen (its menu, pause, the retry screen: the picture keeps its old shape with bars until the loop is left), and the first loading screen of a game is drawn before any change. On a phone held upright the view from side to side is narrow (26 degrees at 412 x 915: the JavaScript port's rule), a scene's bars are three times as thick, and the game spreads its own screens over the height (its menu's entries stay in the upper third). The engine's Arial font keeps the size of the width it was made at.
- Camera lift: the pass in which it takes over at a wall is one step of about 17 units when RedCat backs in at full speed (the original's own pull-in there is as large); the low-ceiling and not-drawn cases were only run on the JavaScript port's test cases, not in a level.
- Looking around and first person: when a cutscene or fixed camera starts, one frame is drawn without RedCat; keyboard turns keep the camera's original lag; shots stay level whatever the look pitch; looking far up in third person puts the camera on the floor; a CameraTrigger was not walked into (the modes were set with the game's own calls).

- Hosting: the package and its server configuration were only run behind a stand-in server, not nginx, and nothing is on the public site (`docs/hosting.md`). Firefox and Safari themselves were never run (Playwright's Firefox and its Linux WebKit once, milestone 31). No page with the privacy text, donation addresses and links that the JavaScript port has under Over. The change to the next world inside an adventure still fetches that world's own files one by one. No desktop or Android build.

In Firefox the `load` event of a page opened within some 30 ms of a game ending on the page before never comes (the tab keeps its loading mark; the game runs): the page must not wait for `load` before starting a game, which was tried and made the game not start. - The game thread's memory is a fixed 192 MB of address space (159 MB of heap). Left as it is; a phone that cannot reserve it fails at the start. Not reached in any run; giving the bytes back changes both hashes of the README pair, so it waits for a change that does that anyway.

- Save states made before the review fixes of 2026-11-14 (milestone 23) are dropped once (`STATE_ABI` 2), and again by the hand torches of milestone 29 (`STATE_ABI` 3: a new part of a state; the part's name is in a state's identity anyway, so the drop follows from the format rule). - A state that passes every check and then makes the game hang (not fail) is not detected: there is no watchdog on frames, because a hidden or paused page draws none either. A page that dies while continuing is counted, and the state dropped after the second time in a row.
- Muziek and Geluidseffecten over a running game take effect when the game goes on (it waits while the settings are open), without the menu's clips; nothing of it was heard in a browser.
- Two tabs: settings, player files and the menu's notes follow each other, but a game that runs in one tab keeps writing its own player's file, a player deleted in the other tab comes back when that game writes his file, and the saved places (IndexedDB) are per player number whichever tab made them. A value that only fits in IndexedDB (a full localStorage) is not seen by the other tab until its next visit.
- Phones held upright: the picture fills the screen (row 42) and the gear, Camera and the frame counter lie over its right edge under the HUD; the insets of a notch or a home bar are left free by reading `env()`, which no run could set; on a phone of 360 by 640 the longest line of the game (three sentences) reaches the Menu button from below.

- The fixes of milestone 25 were run in the Node runner only, with RedCat put in place by the host (free flight, `SetPosition`), not played to: nothing of them was heard or seen in play, and no enemy was caught in a real explosion. The wall strips of the Graveyard look the same with the fix on and off. Larger far shots are not done ("Open decisions" above).
