# Guide for continuing this project

Read this before changing anything. [`../PLAN.md`](../PLAN.md) has the state and the next actions.

## What this is

*RedCat Spookkasteel* (Davilex, 2000) in the browser, made by statically recompiling the original game module `RcHcGame.dat` to WebAssembly. The module contains the game (`CRC…` classes), Davilex's "Adam" layer (`CAdam…`, `CDavi…`), the Davi-Script runtime and the Genesis3D engine, all statically linked. None of it is rewritten. The port supplies what the module asks of Windows.

## Rules

- **Originals are read-only.** The original files, the Ghidra function lists and the decompiled code are in `../RCSPOOK_NEW/RC_ORIGINAL_DECOMPILED/`. Never write there, and never write to the original installation.
- **Do not edit generated files**: `public/game/*`, `tools/out/*`.
- **Evidence before behaviour.** When the game needs something from the host, find what the original code expects in the decompilation (`decompiled/RcHcGame.dat/functions/<address>_*.c`, `assembly.tsv`) and write the address next to the implementation. Do not return success from a call that is not implemented.
- **Keep "implemented" and "verified" apart** in `PLAN.md`. Headless Chromium is the reference; Playwright's Firefox and its Linux build of WebKit were run once (2026-11-14, "Other browsers" below); no real Firefox, no Safari, no phone.
- No commits, pushes or releases unless the owner asks.

## Architecture

```
page (source/web/main.js)                          game worker (source/web/worker.js)
  <canvas>, drawn by the render worker              source/render/remote.js: writes down each frame's <- gdriver.js <-+
    (render-worker.js -> source/render/webgl.js) <-   render calls, one message per frame on a MessagePort            |
  Web Audio (audio.js)     <- postMessage           <-  dsound.js                                             |
  keys, mouse              -> shared ring           ->  user32.js, dinput.js                                  +-- spook.wasm
  IndexedDB (save state)   <- postMessage           <-  snapshot.js, mainloop.js                              |   (RcHcGame.dat)
  localStorage (INI files) <- postMessage           <-  kernel32*.js, vfs.js: original files by sync XHR  ----+
```

- **The worker never returns to its event loop while the game runs.** It sits in the original `WinMain`. Input reaches it only through the shared ring (`shared.js`), which is why the page must be cross-origin isolated. The frame wait in `worker.js` (`platform.frame`) is the only place the game thread sleeps.
- **Nothing of the GPU may live in, or leave, the game thread.** A browser frees a picture that crossed threads (an `ImageBitmap`, a `VideoFrame`) only when the thread that made it returns to its event loop, and this one never does: handing each frame to the page leaked a full-size surface per frame (about 500 MB per second at 1920×1080). Drawing on a transferred canvas from the game thread never shows anything, for the same reason. So the driver's `host.render` in the browser is a recorder (`source/render/remote.js`): it writes the frame's calls into one buffer (commands, all vertices, all indices, small pixel data; larger texture pixels are transferred as they are; the buffer is one of two shared ones used in turn, so that a frame leaves nothing to collect) and posts it at `EndScene` to the **render worker** (`source/web/render-worker.js`), which owns the page's canvas (`transferControlToOffscreen`, once per canvas: one render worker for the page's lifetime, reset per game), returns to its event loop after every frame, and replays the calls on the WebGL renderer (`source/render/webgl.js`). What the game thread needs back is in the shared control words (`CTRL` in `shared.js`: frames drawn, drawing size, a dead render worker, a WebGL context that came back, how busy the graphics chip is): it cannot receive messages. `render.pace()` in `platform.frame` keeps the game thread at most one frame ahead; it never waits without end (pause, close, a dead or hanging render worker). After a lost WebGL context or a render worker that hung, the recorder starts the renderer from nothing and calls `gdriver.reupload()`; between a context coming back and that fresh start the renderer draws nothing (`stale` in `webgl.js`: the frames on their way would be drawn without textures). A context that stays away for five seconds of a game that is not paused ends the game as an error (`render-worker.js`), and the next game gets a new canvas. Lost and back under a paused game, the canvas stays black until the game goes on: only the game can draw its picture again. Nothing flows from the renderer into game memory. After changing any of this: `node tools/gpu-memory-check.mjs` (memory, frames, and that the picture shows the game and moves) and `node tools/render-check.mjs` (settings, context loss, a failing or hanging render worker, restart, save and continue); the Node runner has no renderer and cannot see it.
- **Imports** are bound by name with `m.api('DLL!Name', nargs, fn)`. `nargs` must be the real stdcall argument count: a wrong count corrupts the stack silently.
- **Host libraries.** DLLs the game loads at run time are answered by `host.virtualLibs` (`kernel32.js`): `D3DDrv.dll` (the render driver) and `DSOUND.DLL`. `SoftDrv.dll` and `GlideDrv.dll` are reported missing on purpose: a working Glide driver would hide the D3D one.
- **The render driver** (`gdriver.js`) is `__fastcall` on every slot, with the stack clean-up of the original functions. It keeps the original driver's two polygon queues and flush points, because the original does not draw in submission order. Texture pixels stay in game memory; the renderer is told when to re-read them. The engine unlocks levels it did not write to (the game's own menu: all its bitmaps, every frame), so `sync()` keeps two checksums of each level's bytes and does not send a level the renderer already has; these are renderer-side only, not in a save state, and forgotten by `reupload()`.
- **The main loop** is run by `mainloop.js` through the hook on 0x4BFD60. Everything inside one pass is original code, including the nested loops (in-game menu 0x52EC30, pause 0x534D00, retry 0x5351E0, results 0x52E620, fades, loading refresh). A pass of play presents one frame; `mainLoop.frames` counts them, and a second frame in one pass means the game is in a loop of its own: `mainLoop.onNested` functions run then (inside game code: they may only read and write memory), and the page hears it as bit 8 of `CTRL.SCENE` (`game.scene().nested`), with which loop it is in bits 4 and 5 (`game.scene().own`: `'menu'`, `'pause'`, `'retry'` or `''`; `worker.js` `ownLoop` finds the nearest return address into 0x52EC30, 0x534D00 or 0x5351E0 on the game's stack, reading only). The touch controls differ per screen by it (`touch.js`), and are taken away while a world loads (`game.scene().state` 1); `touch.js` also writes the screen on `<html data-game-screen>` (loading, menu, pause, retry, results), by which the frame counter is placed. A fade (nested, no own loop named, state 3: between the loading screen and play) is no screen of its own: only the arrows go, the rest and the counter stay as the screen before had them.
- **Save states** (`snapshot.js`) are taken between two passes: memory ranges plus what each host module registered with `host.snap.add`. A module that keeps state in JavaScript must register it, or a restored game will differ. The Node check in the README catches that: the two hashes must be equal. The hash (`memHash` in `tools/run-headless.mjs`) is of the host's low memory, the image, the heap and the pages at the top of memory, where the game's own heap is; a check of your own must cover the pages too, or it does not see the player. The stack below the stack pointer is part of a state although nothing there is live: the game copies locals it never set into lasting data (seen in world 3, not in world 1), so run the pair in world 3 as well.
- **A save state only fits the build that made it, and an unusable one must never reach the player as an error.** The memory in a state holds addresses the host handed out (thunks in the order they were made, low-memory structures, handle numbers), untyped, so a state cannot be converted to another host. Two identities guard this:
  - `host.snap.abi`, fixed by `host.snap.seal()` when the host is put together (`runtime.js`) and written into every state: the translated module's hash (`wasmSha256` in `spook.meta.json`, written by `tools/recomp/build.py`), the layout, every thunk's name, number and stack clean-up, every `lowAlloc` size in order, the vtables, the parts of a state with their versions, and `STATE_ABI`. So: make every thunk, interface and install-time `lowAlloc` before `seal()` (anything made later is not in the identity), give a part whose shape changes a new `version` (fourth argument of `host.snap.add`), and **raise `STATE_ABI` in `snapshot.js` for a change no list shows**: what a value in a part means, the heap allocator, how handles and ids are numbered, the calls of a main-loop pass.
  - the page's `build` on every stored record (`game.js`): the SHA-256 of `spook.meta.json` plus `STATE_ABI`. It lets the page and the menu judge a record before anything is unpacked or started.
  - `host.snap.check(state[, esp])` does everything that can fail and writes nothing: identity, screen size, every part present (a part may add its own `check`), and memory ranges (`spans`) that are exactly the ones a save with the state's own cursors writes. The bytes of a range are stored whole, except in the three ranges `load()` fills with zeros first (the stack below the stack pointer, the heap and the VirtualAlloc pages): there 4 KiB pages of zeros are left out. Do not leave anything out of a range that `load()` does not clear. `load()` calls it first; `unpack()` refuses bytes whose lengths do not add up. All of these throw `StateUnusable`.
  - In the browser (`game.js` "save states", `worker.js`): a record that is malformed, of another build or without one (every state from before 2026-11-13), or that does not unpack to its stored length, is deleted before a game thread exists; `game.saveInfo()` does this too, so the menu never offers it. The game thread checks the state before the game runs and again where the loop stands (`host.onRestoreFailed`); refused there, the booted game simply runs when it is the game the caller asked for, else the page starts that one (`recomp-restart`). A failing `load()` (memory already replaced), a continued game that ends by itself before its state was loaded, and a continued game that ends in an error within its first ten seconds also start the world instead of the error dialog; only in that last case the record is kept for one more try (`rcspook-recomp.resume-tries`). A try is counted when the state has been loaded, not before (the boot before it takes a world's loading time), and not when the page is left or hidden meanwhile. A record whose `launch` the game could not start with is refused by the page like a damaged one. The player always gets the world of the caller's arguments (the menu takes it from `Player<N>.ini`), never the launch stored with the state, and a line on screen for twelve seconds of game (`#game-notice`, event `recomp-notice`). There is deliberately no watchdog on frames: a hidden or paused page draws none.
  - The page judges a record by the game's lists (`spook.meta.json`, asked for up to four times). While those do not arrive a record is neither offered nor dropped: `game.saveUnknown(player)` says so, the menu asks again every few seconds and before it starts a game, and starts none over such a record (`menu.js` `refreshSaves`, `launch`).
  - When the page is hidden it asks for a state and pauses in one go. The game thread finishes the pass it is in and takes the state before it pauses (`frame()` in `worker.js`, at most three frames; a game inside one of its own loops, such as its menu, cannot save and pauses at once).
  - A game that ends by itself (its own menu, the end of an adventure) with its player file further than the stored state (another world, a world completed: `placeOf` in `game.js`) loses that state: continuing would put the older file back over the newer one. The gear's "Spel stoppen" takes a state first.
  - A restore puts back the game's own files and the playing player's file, with the name and the two volumes the menu has now. Other players' `Player<N>.ini` stay as the page has them, and a player deleted since does not come back (`kernel32.js`, the `kernel32` part).
  - **When a state is taken, and when not** (`worker.js` `onPass`, `mainloop.js`): when the page asks (F5, the timer, a hidden page) and when a pass changed the sublevel (`loop.changed`, set after `ChangeToSubLevel` returned: the next world of an adventure, or the same world again after "Ja" on the retry screen). Never while `loop.saveBlocked()` answers: `'quit'` (the quit flag `app+0x3E`: the request is dropped) or `'dead'` (RedCat's health is 0 or less: the request stays and is taken at the first pass he lives again). The page hears `'state-skipped'` (event `recomp-save-skipped`). What the game does around a death and a change of world was run, not guessed: `docs/research/startup-and-loop.md` 8.
  - **Kinds of record** (`slot()` in `game.js`): `player<n>` the saved place of the adventure, `player<n>.quick` a Snelspel's (only for the Snelspel that runs; deleted when it ends, when another starts, and by `game.forgetSnelspel()` when the menu loads), `player<n>.r1` to `.r3` recovery points (`recovery.js` has the rule and the storage budget; `rotateRecovery` copies stored records before a new state replaces the newest). Every record carries `play`, the player's playing time in seconds at the save; it only runs while his game runs and never goes back. `game.reload()` (F9, the settings over a game) puts the saved place in place of the running game; leaving a continued game that way is not a failed try (`leave()` clears the count, as leaving the page does). A record's `launch.world` follows the player file, so a state taken after a change of world is booted in that world.
  - **The player file says where an adventure is**: `[Level1] CurrentSubLevel`, and the adventure is finished when `[SubLevel1_5] Completed` is set (`players.js`). `[Level1] Completed` is set by the game at every change of world (`0x497C97`) and says nothing about the end.
  - After changing any of this: `node tools/savestate-check.mjs`.
- **The page API** (`source/web/game.js`, also `window.RecompGame`) is what a menu or a test drives: `game.start({ player, world, difficulty, adventure, resume })`, `game.save()`, `game.reload()`, `game.saveInfo(player)`, `game.recoveryInfo(player)`, `game.loadRecovery(player, id)`, `game.deleteSave(player)`, `game.players` (the original's `Settings\Player<N>.ini` files, kept in localStorage by `files.js`), `game.settings` (the port's own settings), `game.cheats`, `game.input` (keys and mouse movement for controller and touch code).
- **The game's screen** is 480 lines high and 640 to 1280 wide (`chooseLogicalWidth` in `game.js`), fixed when a game starts and stored with a save state; the host reports it as the mode named "640x480" (`gdriver.js`). The drawing size is independent, in pixels: `drawSize()` in `game.js`, sent as `render.configure(width, height, msaa)`, which applies from the next frame. **Anything that limits the drawing (a budget, a cap, the render scale) belongs in `drawSize()`, never in `outputSize()` or `chooseLogicalWidth()`**: those decide the game's screen width.
- **"Low End PC"**: the game sets its setting `IsLowEndPC` at its start (0x4BE08C) when `[Display] Mode` of the player's file is 0 or 1, and then leaves out the fairy's stars, ribbons and light itself and shortens every object's range (`docs/research/effects-low-end.md`). `applyLaunch` writes `Mode=2`, which is what the original's menu gives a new player (`RcHcMenu.dat` 0x56B850, `static.ini` `[DEFAULTSETTINGS] Resolution=2`; 1 is only that call's fallback). Her loose stars (pool at `fairy+0x548`) are made only while she flies a path, and in the Forest's lesson that depends on the frame rate in the original code: none at 60 a second. A new player's file comes from `PlayerDef.ini` (`Mode=0`), the Node runner's player 1 from the shipped `Player1.ini` (`Mode=2`): a check that must see what the browser sees uses `--player 2`, as `tools/effects-check.mjs` does. When an effect is missing, ask the game first what it offered the driver (`tools/effects-plugin.mjs`) before looking at the renderer.
- **Phones and tablets** (`source/web/device.js`: the JavaScript port's rule, also used for the touch controls) get that port's profile: the automatic resolution draws within 540 lines and 960×540 pixels (`drawSize()`; "Volle schermresolutie" and a chosen resolution do not), MSAA starts at off (`settings.js`, once per visitor, mark `phoneMsaaChecked`), the display's ticks are limited to 60 per second, (on every device since 2026-11-14) the render scale steps down by 25 points with MSAA off after three seconds under 30 frames per second while the graphics chip was at work for at least half of the time (`quality` in `game.js`; `busy` in the statistics, measured in the render worker with a sync fence after each frame, `takeBusy` in `webgl.js`), and the save state by itself comes every three minutes instead of every minute. The game thread's own waiting (`idle`) does not tell a slow chip from a display that gives few ticks: both show as waiting for the display. A desktop keeps its other defaults. After changing any of this: `node tools/phone-check.mjs`.
- **Memory the port lets go of.** A phone's browser ends a page that takes too much, so nothing large is kept twice: the original files are let go once the game has not read from them for a few seconds and fetched again if it does (`worker.js`, `sweep()`; this is why the files must be cacheable, `docs/hosting.md`); the page's mixer keeps a sound's samples once, raw until the first play and decoded after it, and a duplicated buffer shares its original's (`audio.js`, the `alias` message of `dsound.js`); a save state leaves the game thread in the pieces it was copied in and is compressed and stored as a stream (`snap.pieces()`, `storeState()` in `game.js`); the driver's polygon queues and the frame buffers are made once (`gdriver.js`, `remote.js`).
- **Controller and touch** (`gamepad.js`, `touch.js`) produce keys, mouse movement and a stick's value through `game.input`. `holdKeys(source, keys, down)` counts holders per key, so two sources can hold the same key; the keys are the ones the playing player's file has for an action (`game.input.vks('jump')`, `keybinds.js`). `setStick(source, x, y)` holds the forward or back key and sends the value (`EV.STICK`); `setWalk` asks for walking slowly (`SET.WALK`). `gamepad.inUse` says whether the controller is what the player works with now (a button or stick sets it, a real key or pointer takes it away): the prompts over a running game ask that, not the menu's `body.controller-input`, which nothing keeps up during a game. In the game thread both end in `source/host/move.js`: two host hooks (the steering 0x434430, `CRCPlayer::Move` 0x435490) that call the original and nothing else unless a stick is deflected or walk is held. The stick's value is input of the moment and not part of a save state. `move.state()` (in the statistics once a second: `game.stats.control`, `.cutscene`, `.speed`) tells the page whether the player has the controls. Research and what was measured: `docs/research/input.md`; after changing any of it: `node tools/input-check.mjs`.
- **Keys** are the game's own: `[KeyBinds]` in the player's file, written by the menu's form (`source/menu/key-menu.js`) and by the game's Spelbesturing page. Do not put a key table in front of the game again. A restored state gets the lines the file has now (`kernel32.js` `MENU_KEYS`, `host.keysChanged`, `move.js`). The setting `keys` only holds the camera key every player starts with (`camera`), each player's own (`cameraBy`), the JavaScript port's old bindings (`legacy`) and the mark `v: 3` (given once the players of before had their keys; it is not in the settings' defaults, and `v: 2` of an earlier build marks nothing). A key of Walk that another action uses inside a combination (the original's Alt) is not watched as "walk slowly" (`walkKeys`).
- **Skipping a scene** (`source/host/skip.js`, `source/web/skip.js`, `docs/research/cutscenes.md` 2): the scene is played to its end by the original code in passes of half a second of game time (`SKIP_STEP`, 500 ms: the most `CAdamSubLevel::Update` 0x4F5170 simulates in one pass, as four updates of 125 ms), without the engine's `RenderScene` 0x5B88D0 (host hook `renderscene`: it answers 1 while a skip runs; everything around it runs, the visibility, the lights, the end of the one-frame polygons, the HUD, the bars). `host.onFrame` asks `host.skip.frame()` for the step and hands it to `platform.frame(step)`: with a step the platform adds it to its clock and waits for nothing (the browser: `skipClock` in `worker.js`; `render.thin`, switched on by `skip.onStart` before the first skipped pass draws, so the canvas keeps the scene's last picture; the Node runner: its virtual clock). While RedCat himself is being moved during a skipped scene the passes are 33⅓ ms again (`SKIP_FINE_STEP`; no scene the check runs does that). A skip ends at cutscene state 0, not at 3, and runs on while the scene has left something running (a fairy that was busy during the skip, a timed camera; `SKIP_TAIL_MS`): a new kind of leftover is added there as a read of the game's own state, never as a write. Never write game memory or call game functions to end a scene. **The standard is not byte equality with one frame rate** (that is what the save-state pair demands, and only that pair): `node tools/skip-check.mjs` (also `--fixes off`; `--sweep` for 25 more scenes) demands (1) a skip that draws (`host.skip.draw`) = the game played with the same clock steps without the skip module, byte for byte; (2) the skip without `RenderScene` against the one with it: every object's state the same, differences only in the renderer's working tables and in where allocations land; (3) against the scene watched at 60 frames a second: RedCat, what he has, and every script object's word on which runs at 60, 50 and 40 frames a second agree. Something that fails (3) is added to `RATE` in the check only with a run of the original that shows it depends on the frame rate. After changing the step, the hook or what a pass of a skip leaves out: that check both ways, and the README's save-state pair (the hook must change nothing outside a skip). Sound during a skip: `dsound.mute` (the game's calls go on, nothing is started on the page, the level's music is left playing there, and afterwards only loops are started at their place). The page silences its mixer the moment the hold is complete (`sceneCover` in `game.js`, `hush` in `audio.js`) and does not hide the picture; the circle of "Overslaan" stays over the held picture until the first frame after the skip is drawn (`game.scene().held`; the game thread sends that frame's number) and turns (`.busy`) only when the skip takes long: the game thread's estimate after three passes (bit 64 of `CTRL.SCENE`) or 250 ms gone by. The page learns the cutscene's state every frame from `CTRL.SCENE` (`game.scene()`), asks with `EV.SKIP`, and lets no input through while a skip runs. A request is taken between two passes; inside one of the game's own loops (its pause, P, works during a scene; its menu does not open there) none comes, and the page takes the request back after 0.8 s (`EV.SKIP` 2).
- **The subtitle box** (`source/host/subtitles.js`): a `late` host hook on `CRcCutScene`'s draw; with the setting off it calls the body and nothing else. With it on the body runs as it is and the render driver leaves the letters out (`host.subtitles.hide()` in `gdriver.js` `RenderMiscTexturePoly`): the module writes nothing into game memory, and the memory must be the same with the box on and off (`tools/fixes-check.mjs --only subtitle`). The line is read after the original ran and posted to the page (`'subtitle'`), which shows `#subtitle`. A line is gone when a frame passes in which the game did not draw it.
- **What the page puts over the picture** is checked by `node tools/screens-check.mjs` (headless Chromium): the skip with key, controller and touch, the subtitle box, the frame counter, "Overslaan" inside the game's own pause, full screen and its first click, the Esc a browser keeps, a window that is not in front, the MSAA note, the intro again, the port's help page, the results screen, the touch controls over the game's own screens (`gamemenu`), every page control against the others and against the game's titles and text in every screen of a phone on its side (915, 844, 740 and 667 wide), a phone upright and a tablet upright with the frame counter on, with the first-time hint and a notice of the port (`overlaps`; `--before tools/out/overlaps/before` runs it on the layout of before 2026-11-15, where it must fail) and the menu's own pages (`layout`, which looks for the paw buttons' artwork in a screenshot: do not use `border-image` inside a zoomed form, Firefox draws it unscaled). A headless browser enters full screen without a click and has `document.hasFocus()` true for every page: the check puts the real rules back where it needs them; other checks store `fullscreen: false` or do not care.
- **Pauses** (`pause` in `game.js`): `hidden` (the tab), `blur` (the window is not in front; set only when `document.hasFocus()` is false at the blur event), `user` (`game.setPaused`, a dialog over the game). Any of them stops the game thread and its clock and lets go of every key. `swallowedEscape()` gives the game the Esc a browser kept (mouse let go, full screen left); the page's own `exitPointerLock` and `exitFullscreen` calls mark themselves (`ownExit`, `fsOwnExit`) so that they are not taken for the player's.
- **The two volumes** (`source/host/volume.js`): Muziek and Geluidseffecten while a game runs and after a restore, through the game's own setters between two passes; nothing is called while they are unchanged. Check: the Node part of `tools/savestate-check.mjs`.
- **Cheats** (`source/host/cheats.js`) switch what the original already has: its no-clip byte, its god-mode byte, its hidden cheat page, and its add-potion, add-mirror-part and add-score functions. Requests are queued and applied in `mainLoop.beforePass`, between two passes.
- **Launch settings** (`ini.js`, `applyLaunch`) write what the original menu and launcher leave for the game: `Settings\Game.ini [Run]`, the player file, `Computer.ini`, and the reset of the original's crash guard in `Startup.INI`.
- **Looking around and first person** (`source/host/look.js`, `docs/research/camera-and-look.md`): requests from the page (`EV.LOOK`, `SET.FIRST_PERSON`) are applied between two passes, on the original follow camera's own data. Field of view is a launch setting (`ini.js`): the engine's `FieldOfView` is width / scale, not an angle. After changing either: `node tools/look-check.mjs`. The camera lift at walls (`walllift.js`) is a host hook on the camera controller's frame (`GAME_HOOKS` in `tools/recomp/build.py`: the host runs the original function and then acts on its result); check with `node tools/walllift-check.mjs`.
- **Fixes of original faults** (`source/host/fixes.js`, `docs/research/original-fixes.md`): the only place where what the original computes is changed on purpose. One flag per fix in `FIX_DEFAULTS`; `host.options.fixes` (`'off'`, `'name=0,…'`, an object) overrides, the page sends its settings as `init.fixes` and later changes as `SET.FIX`. A new fix needs: the run that shows the fault on the original code, a flag, a scenario in `tools/fixes-plugin.mjs` and its checks in `tools/fixes-check.mjs`, a row in `docs/intentional-differences.md`. With every flag off the game's memory must stay the original game's (`307574ef` for the README pair with `--fixes off`; with the fixes on the pair prints `8f54e89b`, and `tools/fixes-check.mjs` demands that the two differ): no low memory taken, new hooks `late`. Run the sound comparisons with the original with `--fixes off`.
- **Two picture-only flags in the same list** (`skyBackdrop`, `smoothSprites`; `docs/research/effects-low-end.md` 7): the driver draws the scene's sky box behind the world at `BeginWorld` (read from `RenderScene`'s SkyInfo on the game's stack; the original leaves a view past the level's faces black) and smooths the sixteen levels of a 4444 texture's channels in `pixels()` (`source/host/smooth.js`; the original's surfaces have 4 bits). They read game memory and write none, so the hashes are the same on and off (`node tools/fixes-check.mjs --only picture`), and they are not faults of the original but its picture made better: off is what the original draws. `smooth.js` keeps every texel inside the sixteen values its level stands for; do not loosen that without the comparison against the original bitmaps (`tools/out/halohud/fix-halo/eval2.mjs`). After changing either: `node tools/effects-check.mjs` (the lesson's close-ups: no black around her halo, no step in its edge; look at the pictures).
- **A third picture-only flag, `hudShape`** (`docs/research/genesis-driver.md` 11b): in a mode that is not 4:3 the driver gives the game's 2D bitmaps their 4:3 width again, in its own copy of the corners at `RenderMiscTexturePoly`. A bitmap is known by the return addresses on the game's stack (`DrawBitmap` 0x5614E0 and its caller), and each caller has its rule in `reshape`; a caller without a rule is drawn as the game gives it. A new screen with 2D needs its caller added there and in `tools/hud-check.mjs` (which fails on a caller it does not know). After changing it: `node tools/hud-check.mjs` (it must fail with `--fixes hudShape=0`), `node tools/fixes-check.mjs --only picture`.
- **The hand torches** (`source/host/torches.js`, flag `handTorches`; `docs/research/original-fixes.md` 10): the one fix that writes game memory every frame while it is on. It moves the birth places of sixteen authored flames between two passes, hands the engine polygons for the other sixteen at the driver's first `BeginWorld` of a scene (`geWorld_AddPolyOnce` 0x5B6E90), and borrows free slots of the engine's dynamic-light table from `BeginScene` to `EndScene` (lightmaps are computed inside the engine, so the driver alone cannot light a wall). It gives the one hand without a motion (Graveyard `AdamAnyActor131`) the motion `anim` through the game's own set-motion 0x4A06B0 on the hand's animator (`hand+0x19C`), once. It walks the sublevel's object list before every use: a hand that is shot is destructed inside the pass. When it pairs hands and emitters again in the same sublevel it keeps the level's birth places it already knows (never read the places the host moved as the level's). Its pools, the authored birth places and the hand that got a motion are the part `torches` of a state. The calls inside a scene run 0x1000 below the driver's stack pointer and leave other dead stack than the original. After changing it: `node tools/fixes-check.mjs --only handTorches,state`, the README pair, `node tools/savestate-check.mjs`, and `node tools/torches-check.mjs` (pictures: look at them), and for the cost `node tools/gpu-memory-check.mjs --torch castle` and `--torch yard` (the checks that stand at a world's start do not reach a hand in the Castle).
- **Small persistent values** (`persist.js`): settings, the game's INI files and the menu's notes go through `store`, which writes localStorage and IndexedDB and takes the newer of the two at the next visit. Two tabs share them: what another tab wrote is taken over at its `storage` event, and `files.js` re-reads the stored value (`store.fresh`) before it changes one file of it (`node tools/menu-check.mjs --only tabs`). Do not call `localStorage` directly for this port's own data.
- **Files and hosting** (`source/web/worker.js`, `docs/hosting.md`): the game thread fetches a world's start files together before the game starts (`game/preload.json`, measured by `tools/build-preload.mjs`); every other file is fetched whole on first use while the game waits; the page fetches likely later files in the background. No byte ranges. The game module's folder is found relative to the scripts (`gameUrl` in `game.js`), the original files and the menu's assets relative to the page: keep it that way, the package puts scripts and game module under `app/<revision>/` and everything else beside `index.html`. `tools/package.mjs` builds `dist/site`, `tools/serve-site.mjs` stands in for the web server, `tools/package-check.mjs` checks the result. `tools/site-check.mjs` checks a real server against the package. The live server keeps the two ports in sibling folders (`redcat-recomp/`, `redcat-website/` served at `classic/`); the JavaScript port's deploy script mirrors `redcat-website/` with delete, so never put this port's files there. Checks that load a module in the page must take its address from the page's own script tag, not `/source/…`.
- **The JavaScript port's data** (`legacy.js`, `legacy-import.js`, `docs/legacy-saves.md`): read only, taken over once. Never write a key that starts with `redcat.` and never open a `redcat-recovery-saves` database with a version number. After changing any of this: `node tools/legacy-check.mjs`.
- **Files.** The virtual drive `C:\REDCAT` holds the original files, mounted read-only and fetched on first use. A file the game opens for writing becomes a private copy (`vfs.makeWritable`); copies are handed to the platform to keep (`persistFile`). The game's own logs are not kept.

## How to work on it

1. Reproduce in Node first: `node tools/run-headless.mjs --seconds 30 --fresh --world N --trace debug`. Time is virtual, so half a minute takes a few seconds. The game's logs land in `tools/out/logs/`; compare `ADAMDEBUGNN.LOG` with the `AdamDebug*.log` files of the original installation.
2. A missing Windows call stops with "Host function not implemented: DLL!Name"; a missing driver slot or COM method names itself the same way. A call through a pointer to code that was not recompiled stops in `BAD_INDIRECT_CALL`, and `g_a` in the runner's output is the target address: add it as an entry (`docs/recompiler.md`).
3. Then the browser: `node tools/serve.mjs` (port 4221, see "Other browsers"), and `node tools/browser-check.mjs` for screenshots; `node tools/gpu-memory-check.mjs` and `node tools/render-check.mjs` after touching how frames reach the screen. The built-in browser pane of the Claude desktop app has no WebGL, so it cannot show the game.
4. After changing `tools/recomp/*`: `npm run recompile`. After changing which original files exist: `node tools/build-manifest.mjs`. After either, or after changing how the host reads files: `npm run preload` (the per-world file lists).
5. After changing any host module's state: run the save-state check (the README pair, hashes equal) and `node tools/savestate-check.mjs`; raise `STATE_ABI` or the part's version when states of the build before no longer fit. After changing `dsound.js` or `audio.js`: `--check-sound`, the comparison in `docs/research/sound.md`, and `node tools/phone-check.mjs` (what the page's mixer keeps). After changing the render driver's queues (`gdriver.js`): the driver must hand the renderer the same calls as before; a run-headless plugin that hashes them is enough (`host.render` is free in the Node runner; hash the texture pixels the renderer holds at each draw rather than the uploads, which `sync()` may leave out).

## Other browsers

Tried once, on 2026-11-14, in Playwright's Firefox 146 and Playwright's WebKit 26. **That WebKit is the Linux build of Safari's engine, not Safari**: nothing seen there is a statement about Safari on a Mac or an iPhone, in either direction. The findings and their independent verdicts are summarised in `PLAN.md` (milestone 31, "Not verified", "Known gaps").

- **The development server's port is 4221, not 4190** (`DEV_PORT`, `DEV_URL` in `tools/dev-port.mjs`; `tools/serve.mjs` and every check take their default from there). 4190 is on the list of ports that Firefox and WebKit refuse to open whatever listens there ("This address is restricted", "Not allowed to use restricted network port 4190"); only Chromium opened the page, so every result from those two engines on 4190 was a page that never loaded. Do not move the default back, and check a new number against both lists. A page's storage belongs to its address with the port: players and save states made in a browser of your own under `:4190` stay there (`node tools/serve.mjs --port 4190`, Chromium). `tools/serve-site.mjs` keeps 4195, which nothing blocks.
- **One launcher for the checks**: `tools/browsers.mjs`, option `--browser chromium|firefox|webkit` (default chromium) in browser-check, menu-check, savestate-check, render-check, screens-check, input-check, phone-check, legacy-check, torches-check (gpu-memory-check is Chromium's process list and says so). Chromium gets Playwright's own browser, untouched. What an engine cannot do prints `not run in <engine>: …` and is counted at the end; never leave a part out without that line (`notRun`, `chromiumOnly`, `canPatch`). What differs:
  - Firefox and WebKit: Esc on a page in full screen leaves full screen and never reaches the page, as in a real browser (Playwright's Chromium hands it to the page). A check that means the page's Esc wraps its page in `escThroughFullscreen(page)` (menu-check); a check of leaving full screen itself does not. Headless Firefox's full screen is 1366x768 whatever the viewport: a case about how a window of a given size is filled stores `fullscreen: false` there and prints the `not run` line (phone-check's desktop sizes, input-check's phone layouts).
  - Firefox: no `isMobile` (a Firefox for Android user agent with touch stands in; no device pixel ratio), no CDP, and `context.route()` does not see what a worker imports (`source/render/*`, `source/host/*`): a change made that way would silently not apply, so ask `canPatch(file)`. The window's `load` event may never come on the page opened right after a page that stopped a game (a menu voice clip of the page being left stays in the load group; nothing in the port waits for `load`), so the launcher's `goto` waits for `domcontentloaded`. **Do not make the page wait for `load` before it starts a game**: tried, and the game then never starts in that sequence.
  - WebKit (Linux build): WebGL in a worker is switched off there (`AllowWebGLInWorkers`; on in Safari), so the launcher starts every context as a browser of its own with `--features=+AllowWebGLInWorkers`, and only the first page of a context has it. Without the flag `game.supported()` is false with reason `webgl2`. Its web process dies at random while a world is drawn (also on a canvas of the page, also without the sync fence): a check that runs longer than a minute seldom ends. The launcher prints `web process died in webkit` for each death and, when the check ends with an error after one, a last line that says so: read a WebKit run from those lines, not from its exit code. `isMobile` keeps a Mac user agent there, so the launcher gives such a context an iPhone's (the port's phone rule reads the user agent). `AudioContext.resume()` holds the page's main thread for seconds in this build (the OK that ends a pause returned after 5 to 9 s): the launcher gives WebKit 90 s where Playwright gives 30. Its profiles (`tools/out/browser-profiles/`) are removed when the process ends and swept at the next launch.
- **What the port does because of it** (all page side; the game thread, original behaviour and save states are untouched):
  - `render-worker.js` answers a frame message that arrives unreadable (`messageerror`: Firefox, for a frame that waited while the render worker hung for seconds) as a drawn frame plus `CTRL.RESTORED`, so the recorder starts the renderer from nothing. Without it the picture stood still for good. `node tools/render-check.mjs --only stall`.
  - `navigator.storage.persist()` is asked by the menu (`source/web/keep-storage.js`), never by `begin()` and never in full screen: Firefox shows a question for it, cancels one made while full screen is entered and leaves full screen for one made inside it.
  - The first-time hint counts its four seconds from the first report with a world, and ignores the numbers of the game before (`hints.js`). A notice's twelve seconds count from the first report with a world of that game thread (`worldSeen` in `game.js`), with sixty seconds as the limit for a game that never reports one (that limit was not run).
  - Firefox lets the mouse go when the page enters full screen. The click that catches the mouse and asks for full screen (a game started without a click) therefore gave: caught, let go, full screen, and the page took the "let go" for the browser's Esc and opened the game's menu. `applyFullscreen()` marks its own request (`ownExit`, `fsAsked`), a mouse let go within a second of it is not an Esc (`fsTookMouse`), and `mouseBack()` asks for the mouse again when full screen is there. A browser that keeps the mouse (Chromium) never gets there. Check: `node tools/screens-check.mjs --browser firefox --only fullscreen,pause`.
  - A storage question that was open when a game was started is cancelled by Firefox (answer false, permission still `prompt`, full screen within a second): the mark becomes `cancelled:<n>` and the next visit asks once more, twice at most (`keep-storage.js`).
  - `?autostart` with `game.supported()` false starts nothing (`main.js`) and the menu treats the visit as an ordinary one (`menu.js`, `mode`), so the visitor gets the notice and not the error dialog.
  - `audio.js` catches the promises of `suspend` and `resume` (Firefox rejects a pending suspend when the page is left).
  - The render worker asks for its WebGL 2 context up to ten times, 50 ms apart (`webgl.js`), and the page asks its own WebGL questions before a render worker exists (`begin()`): in WebKit's Linux build a worker's first ask failed when the page made a context just after that worker was started.
  - `game.unsupportedReason()` (`'isolation'`, `'canvas'`, `'webgl2'` or null; `supported()` is its null) and `game.unsupportedDetail()` for the console. The one-pixel probe context is given back with `loseContext()` on purpose; Firefox writes "WebGL context was lost" for it once per page, which is no fault.
- **Not done, on purpose**: no change for the WebKit process deaths (native, in an engine build that is not Safari), and no allocation "nudge" for its garbage collector (JavaScriptCore let the game thread's heap grow to about 1.7 GB before it collected, then stayed flat; the nudge made it collect sooner there, unproven on Safari). Both are things to measure on a real Mac and iPhone first: ten minutes per world, memory watched (`PLAN.md`). **Update 2026-11-14:** the garbage itself was found and removed: about 2,000 host calls per frame each made a small object (two-value results of hooked functions, argument arrays, a string per 3D voice, a view per batch, the queue sort). Per frame on the game thread in that WebKit build: 90 KB before and 3-4 KB after in world 1, 263 KB and 7 KB in world 2; process memory creeps at 0.3-0.6 MB per second instead of climbing to 1.7-1.9 GB. Same game: hash pair, state files and every recorded frame equal. The peak after the change is a projection (no run lives long enough), 3-7 KB per frame is untraced, and real Safari is unmeasured (`tools/out/webkit-memory-verify/`).

## Likely next problems

- Parts of the game nobody has reached yet may call something the host answers too simply: `DrawTextA` formats, DirectInput (the shipped settings do not use it), joystick, `SetWindowPos` at shutdown.
- Sound: read `docs/research/sound.md` first. The page's mixer (`source/web/audio.js`) only knows what `dsound.js` tells it: any state a buffer gets without a call of its own (a duplicate, a restored state) must be sent with `tell()`, and `--check-sound` in the Node runner catches a mixer that differs from the game's DirectSound state. Buffer positions run on the host clock; if music or speech is cut or doubled, look at `GetStatus` and the `Play` flags. `tools/sound-compare.mjs` puts a trace next to the reference of the original under Wine, and `tools/sound-scenarios.mjs` does that for scripted runs with input: the step script (`run-headless.mjs --script`, the same in `tools/reference-wine/refrun.py`) walks the player to places by reading his position, so port and original take the same route.
- The level change (`CRCGame::ChangeToSubLevel` 0x496D60) chains a fade, the results screen, loading and the intro inside one pass. It has not been run yet.
- Fonts: the game rasterises glyphs through `GetGlyphOutlineA` into its own bitmaps (`gdi32.js`, `source/web/text.js`). Sizes and spacing depend on the browser's font.
