# Intentional differences from the original

What this port does differently on purpose, and what that changes. Things that are merely missing are in [`../PLAN.md`](../PLAN.md).

| Difference | Where | Effect |
|---|---|---|
| **Save states.** The whole game can be saved between two frames and continued later. The original only keeps a player file and restarts a world from its beginning. | `source/host/snapshot.js`, `mainloop.js`; F5, every minute (every three on a phone), when the adventure goes to its next world, when the page is hidden (not from inside the game's own menu or another of its inner loops), **Verder spelen**; F9 and the settings over a game load the saved place again | Asked for by the owner. The original's player file is still written by the game and is part of the state. A game that ends by itself after its player file moved on from the last state (a world finished since) loses that state, and the menu starts the world the file says. A state belongs to one build of this port: after an update that changes the game module or the host, or when the stored record is damaged, it is deleted and the player starts the world his player file says, with a line on screen ("Je opgeslagen plek past niet meer bij deze versie van het spel. Je begint … opnieuw."). Continuing puts back the playing player's file as it was at the save, except his name and the two volumes, which stay as the menu has them; other players' files are not touched. The volumes of a continued game are still the ones it was saved with until the game reads the file again |
| **No save state of a RedCat without health, or of a game that is ending**, as in the JavaScript port from 0.9.9 ("the last living save is preserved"). | `saveBlocked` in `source/host/mainloop.js`, `onPass` in `source/web/worker.js`; evidence in `docs/research/startup-and-loop.md` 8 | The original has no saving inside a world, so nothing of it changes: this only decides when the port takes a state. A state of the two seconds in which RedCat lies dead, stored by the timer, F5 or a hidden page, would with no life left lead straight to the retry screen and replace the last state he could go on from; a state of a game whose quit flag is set (the end of a Snelspel world, "Spel verlaten") would end at once when continued. For a dead RedCat the request waits and the state is taken when he is back; F5 says "Je avontuur is niet opgeslagen. Dat gebeurt zodra RedCat terug is." After **Nee** on the retry screen the saved place is therefore still the last one of a living RedCat, and Avontuur goes on from it, as the JavaScript port chose ("Doorgaan after a game over"); the original would start the world again from the player file, which is offered next to it (next row) |
| **Startinfo → Meer opties: the world again, an older saved place.** "<wereld> opnieuw beginnen" deletes the saved place and starts the world from the player's file; "Eerder opgeslagen avontuur laden" goes back to a recovery point. | `source/menu/menu.js`, `original-menu.js`; `docs/menu.md` | The first is what the original does for a player who comes back, and the way out when the saved place is one from which nothing can be won. The game keeps the state at the door of the world in the player file (seen in the Node runner: closed in the middle of world 1 after a lost life and added points, and after a game over, `[Player]` still had `Life=3`, `Score=0`) |
| **Recovery points**, as an option: next to the saved place of an adventure, three older ones of about 2, 5 and 10 minutes of playing time ago (just before a new state: 2 to 3, 4 to 7 and 8 to 15 minutes; a menu shows the real age). On by default on a desktop, off on a phone or tablet. | setting `recovery` (Meer instellingen → Herstelpunten); `source/web/recovery.js`, `game.js` (`rotateRecovery`, `trimRecovery`) | The JavaScript port kept eleven states, one per minute, and offered those of 2, 5 and 10 minutes ago. A state is 45 to 68 MB here (stored: 23 MB in world 1, 39 MB right after the change to world 2; under 1 MB there), so three are kept and passed down a ladder. Storage: at most three points per player, and all points of all players together at most 320 MB on a desktop and 80 MB on a phone, which is two or three points (the oldest of other players go first, then the player's own oldest); with less than 150 MB of free room the ladder stands still, and when a write fails for lack of room the points go before the saved place does. Moving a point copies a stored record; nothing is unpacked into the page's memory. Points belong to one build of the port like every save state, and they go when their adventure ends, is begun again, or the setting is switched off |
| **A Snelspel never costs the saved place of the adventure.** Its state is kept apart, only serves the Snelspel that runs (F5, F9) and goes when it ends. | `slot()` in `source/web/game.js` | Until 2026-11-14 a Snelspel wrote its state over the adventure's, and nothing could continue from it; Startinfo warned about it. The original keeps the two kinds of game apart as well. A Snelspel record left in the adventure's place by an earlier build is deleted without a word |
| **Griezelplekken stay open.** A world that was reached stays open in Snelspel when a new adventure is begun, and comes along with an imported player. | `noteUnlocked` in `source/menu/menu.js` (the menu's record, `unlocked`) | The original lets the Snelspel cards follow the adventure, so "Opnieuw beginnen" closes them again. The JavaScript port kept unlocks apart from the saved game ("a confirmed new adventure keeps chapter unlocks"), and players taken over from it already had this. The world is noted the moment the adventure reaches it (`recomp-world`), so that an older saved place loaded in the game does not close it again. Only which cards the menu enables; the abilities a world starts with are the game's own |
| **Export and import of one player** in the Spelerlijst. | `source/menu/save-export.js`, `player-menu.js`, `menu.js`; `docs/menu.md` | As in the JavaScript port. The file holds what lasts of a player whatever the build: his `Player<N>.ini` and the menu's record (worlds opened, free flight, last Snelspel choice); not the saved place inside a world, which only the build that made it can load. Imported, an adventure starts at the beginning of the world it is at. Of an imported file only the adventure's sections, the difficulty, the key bindings and the two volumes are taken, every value checked against what the game writes (a key line must be made of the game's own key names and cannot empty a key the new player has; no key twice in a section; health, mirror parts and potions against their maximum as the file will stand); the destination player keeps his name. The JavaScript port's own export file (`redcat-spookkasteel-save`) is read too, with the rules of the take-over |
| **The host runs the top of the main loop.** | `source/host/mainloop.js`, hook on 0x4BFD60 | Same calls in the same order. Left out: the console toggle before the loop (only with `[Debug] DebugUseConsole`) and writing the console state to the INI after it |
| **Render driver in the host** instead of `D3DDrv.dll` on Direct3D. | `source/host/gdriver.js`, `source/render/webgl.js` | Draw order, mip choice, blending, lightmap and fog rules follow the original driver. Differences: lightmaps keep 8 bits per channel (the original reduced them to 16-bit colour), the depth buffer has 24 bits instead of 16, depth is clamped at the near plane instead of left to the display driver, and the 16-bit frame buffer with dithering is a 32-bit one |
| **Resolution, render scale and anti-aliasing.** The picture is drawn at the window's size or at a chosen resolution, times a render scale of 25 to 200 percent, with 0, 2, 4 or 8 samples of MSAA. | settings `resolution`, `renderScale`, `msaa`; `source/web/game.js`, `source/render/webgl.js` | Sharper edges and smoother texture filtering. The game itself still works in a screen 480 lines high; HUD bitmaps and text are enlarged with it. Automatic resolution stops at 2560×1440 worth of pixels. In a window whose shape is a fraction off the game's screen (854×480 in 16:9) the picture fills the window, stretched by at most 0.4 percent, instead of leaving a line open |
| **A profile for phones and tablets**, as in the JavaScript port: automatic resolution within 540 pixels on the short side and 960×540 pixels in all, whichever way the phone is held (412 x 915 at a pixel ratio of 2.6: 483 x 1073; "Volle schermresolutie" uses every pixel), MSAA off to begin with, at most 60 frames per second on a faster display, the save state by itself every three minutes instead of every minute. | `source/web/device.js`, `game.js` (`drawSize`, `limiter`, `quality`), `settings.js` | Asked for by the owner: the game must run on phones as the JavaScript port did. A phone's screen has five times the pixels the budget draws, and its browser ends a page that takes too much memory. The step-down only acts when the graphics chip was at work for at least half of the time, which the JavaScript port did not look at (a display that gives few ticks, as a phone saving power does, lowers nothing here); it changes the two settings, so the menu shows what is in use. Nothing of it reaches the game: the game's own screen is the same |
| **Under 30 frames per second the picture is made smaller, on every device**, as in the JavaScript port: after three seconds the render scale goes down by 25 points (not below 25) and MSAA off. | `quality` in `source/web/game.js`; the lines under Renderschaal and Anti-aliasing (the JavaScript port's wording) | Until 2026-11-14 a phone only. Not in the first seconds of a game, a pause or a skipped scene; only while the graphics chip was at work for at least half of the time (see the row above). Both values are kept as the settings, and an open settings form follows them. Run with software WebGL only (`tools/phone-check.mjs`) |
| **Muziek and Geluidseffecten can be changed while a game runs, and a continued game plays at the volumes the menu has now.** | `source/host/volume.js`, `SET.VOLUME`, `game.setVolumes`; Meer instellingen over a running game | The original reads the two volumes of the player's file once, when the game starts (0x527C20), and has the sliders in its main menu only. Here the values go to the same two calls the game makes then (`CAdamSoundSystem` 0x54E5F0 and 0x54E490, value × 0.01) between two passes, and on OK to the player's file. After a save state is loaded the same happens when the file's volumes are not the state's. Run: every playing sound is at the level of a game started with those volumes (`tools/savestate-check.mjs`). Nothing is called while the volumes are unchanged. Not heard in a browser |
| **The game's screen has the picture's shape, wide or high, and follows it while a game runs.** 480 lines high and 640 (4:3) to 1280 wide (8:3) for a picture of 4:3 or wider; 640 wide and 480 to 1706 high (3:8) for a higher one, a phone held upright (412 x 915: 640 x 1422; a tablet 768 x 1024: 640 x 854; a square window: 640 x 640). The short side is always the original's. | setting `widescreen` (Breedbeeld; off: always 640 x 480); `source/web/game.js` (`modeFor`, `chooseMode`, `sendShape`, `followMode`), `source/host/gdriver.js` (the mode named "640x480" carries the real size), `source/host/ini.js` (`fieldOfView`), `source/host/shape.js`; `docs/research/genesis-driver.md` 11c | The original only offers 4:3 modes and never changes its mode in a running game. **The view from top to bottom stays the original's 54 degrees at every shape** (or the angle of the setting Gezichtsveld): a wide picture adds to the sides, a high one cuts them off (26 degrees from side to side at 412 x 915). The engine's `FieldOfView` is width / scale, not an angle, and `geCamera_SetAttributes` 0x5C9070 projects with the larger of width / Fov and height / Fov (the cameras' scale was read back: 470.59 at 640 x 480 and 854 x 480, 1394.12 at 640 x 1422), so the value written to `AdamWin.Ini` is W x tan / (H / 2) for a wide screen and 2 x tan for a high one. **A phone that is turned, a window that is reshaped:** the page asks the game thread for the new shape; it is made between two passes of the game's main loop, by writing the size where the game keeps it (the engine object, its mode record, the window object, the two cameras) and letting the game's own code make each camera's rectangle (0x556150) and projection (0x5C9070) again. Until then, and while one of the game's own loops is on screen (its menu, its pause, the retry screen: no pass begins there), the picture keeps its old shape with bars. Run: afterwards those objects hold what a game started at that size holds, and the driver gets the same polygons as such a game (byte for byte between 640 and 854 wide over 893 frames; the same vertices in another order to and from 640 x 1422). The game's memory is not that of a game that never changed shape, as two games of different widths differ anyway. **A saved place** is continued in the shape it was saved in and then gets the window's shape the same way, before its first pass: turning the phone between saving and continuing costs nothing, and the record's format is unchanged (a height that is not 480 is stored with it; a record without one is 480). The game's own 2D and text are in the next row. Cutscene cameras that set their own field of view were not checked; the engine's own Arial font keeps the size of the width it was made at |
