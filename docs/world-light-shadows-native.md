# Native dynamic-light shadows on world surfaces

The original `CastShadow` flag now reaches the BSP world-surface renderer as
well as actor floor-ambient sampling. The five authored Tower lights no longer
illuminate lightmap samples through obstructing static level geometry. Baked
lighting and lights without that flag remain unchanged.

## Verified original behavior

The installed `RcHcGame.dat` SHA-256 is
`e30781fcdc665d1f217c1a3353761c96e1ec3566f1ad472bb1a8a499cb29dba5`.
The shadow branch at `0x5d2225` calls `CombineDLightWithRGBMapWithShadow`
(`0x5d31f0`). Each affected integer lightmap sample traces from the light to
the `CalcSurfVectors` (`0x5d4f50`) endpoint, one unit above its oriented face.
The trace call at `0x5d33b1` uses BSP root **0** and solid/window/clip contents
**0x43**. Actors and moving brush models do not cast shadows in this path.

The routine copies the world light position unchanged at `0x5d3229..0x5d322c`.
Its endpoint uses raw authored face coordinates, including the original texture
frame's unusual Z-component origin calculation. Model inverse transformation in
`Light_SetupLights` is used separately to mark potentially affected faces; it
does not transform these obstruction rays. Moving brushes therefore do not
invalidate the visibility cache.

A blocked sample contributes no dynamic light. This rejection happens before
the native fixed-point channel clamp and four-sample interpolation. Multiplying
the finished pixel by a shadow value would incorrectly darken baked lighting
and produce different edges. The existing eight selected world-light limit and
portable floating-point arithmetic remain separate renderer differences.

This comparison used the installed executable and retained Genesis reference
source; it was not a new native-game playthrough. Evidence and bounded assembly
excerpts are retained in
`current_work/world-light-shadows-2026-10-05/native-shadow-contract.md`.

## Implementation and performance

`src/world-light-shadows.js` reuses the imported floor-lighting face metadata,
native point trace and endpoint helper. It reproduces the existing lightmap
atlas packing without changing meshes or importing new assets. Each shadow
lamp owns one obstruction bit in a nearest-sampled, single-channel byte atlas.
Bits follow stable entity identities, independently of the renderer's selected
light-slot order. Four atlas reads provide visibility for all selected lamps.

The Tower atlas is **1024 x 256 (256 KiB)**. Its five stationary lamps need
**2,576 point traces** at their maximum authored radii during loading, including
**1,464 blocked samples**. Color and radius pulses, disabling/re-enabling lamps,
camera motion and streamed geometry residency cause no additional traces or
texture uploads. Moving a light itself, or increasing its maximum radius,
rebuilds only that light's bit. The texture is disposed when the world is closed.

The other four levels contain no authored shadow-casting dynamic lamps. They
allocate no obstruction atlas and retain the shader without shadow sampling.
Player, projectile and added torch lights remain unshadowed, as their flags
specify. No shadow cameras, render passes or per-frame mesh raycasts are added.

## Separate skybox upload error — corrected

**Status:** the loader now normalizes cubemap face dimensions. The same problem
also affected Level 2, Het Kasteel. The campaign audit and resolution are below;
the original failing reports remain available as diagnostic history.

This refers to **Level 5, De Kasteeltoren (`lvl04a`), in the port**. A skybox
is the distant background drawn around the level, using six images as the
faces of a cube. `texSubImage2D` is the WebGL operation that copies an image
into an already allocated GPU texture. It is not a file-loading error or a
shadow-calculation error.

### Exact cause and affected artwork

[`level.json`](../data/levels/lvl04a/level.json) selects sky texture indices
`[27, 27, 28, 28, 28, 28]`. Both the metadata and the PNG headers confirm:

| Cube faces in the current renderer | Original texture name | Imported image | Size |
| --- | --- | --- | --- |
| +X, -X | `sky00` | [`textures/027.png`](../data/levels/lvl04a/textures/027.png) | 128 x 128 |
| +Y, -Y, +Z, -Z | `skyg` | [`textures/028.png`](../data/levels/lvl04a/textures/028.png) | 256 x 256 |

Before the fix, [`CastleWorld.load()`](../src/world.js) passed these images
directly to `new THREE.CubeTexture(faces)` and assigned it to
`scene.background`, without making their dimensions equal. In the installed Three.js implementation,
`uploadCubeTexture()` in
[`WebGLTextures.js`](../node_modules/three/src/renderers/webgl/WebGLTextures.js)
allocates all six faces with `texStorage2D`, using the first image's dimensions:
**128 x 128**. It then attempts to copy each complete image into its face.
The four **256 x 256** uploads exceed the allocated dimensions and are rejected
with **`GL_INVALID_VALUE` (1281 / `0x0501`)**. A cubemap requires equal square
dimensions for all six faces; these individually valid PNGs do not form a
valid cubemap when used directly this way.

### What the diagnostic actually observed

The first test that rendered the normal Tower background captured four failing
`texSubImage2D` calls inside `uploadCubeTexture`, for targets **34071–34074**
(`TEXTURE_CUBE_MAP_POSITIVE_Y`, `NEGATIVE_Y`, `POSITIVE_Z`, `NEGATIVE_Z`).
The error occurred on the first background upload; subsequent draws in that
run did not report another upload error. It was not a shadow-shader compilation
failure. The same direct cube construction exists in the earlier committed
renderer, so “existing” refers to the port's background-loading code, not an
established defect in the original Windows game.

The diagnostic report's final `glError: 0` does not contradict its four recorded
failures: the tracing wrapper calls `getError()` after each GL operation, which
reads and clears that error flag, and stores the failure in `tower.glCalls`.

Rejected uploads leave those faces without their intended artwork. Missing or
dark sky in the affected viewing directions is the expected visual consequence;
the tests did **not** establish its exact appearance during normal gameplay or
any FPS impact. This finding does not mean that the level's walls, floor or
shadow atlas failed to load.

“Unrestricted run” in the earlier wording meant a test with the normal skybox
included, not a different permission or sandbox mode. The final focused shadow
test initially substituted a plain background **in its isolated browser scene
only**. It checked the actual Tower world surfaces and shadow shader with clean
GL checkpoints. The game's runtime background was not replaced. That first
shadow change did not fix the skybox; the subsequent fix described below does.

### Campaign-wide audit and implemented fix

All five level manifests were checked against the actual PNG dimensions:

| Level | Resolved sky faces before the fix | Affected? |
| --- | --- | --- |
| 1 — Het Bos (`lvl00a`) | Six 256 x 256 faces, including the existing missing-face fallback | No |
| 2 — Het Kasteel (`lvl01a`) | `sky00` (`067.png`) and `Air_Wtr00` (`068.png`) are 128 x 128; four `skylv1` (`069.png`) faces are 256 x 256 | **Yes** |
| 3 — Het Kerkhof (`lvl02a`) | Six 256 x 256 faces, including the existing missing-face fallback | No |
| 4 — De Grotten (`lvl03a`) | No authored skybox; all six indices are -1 | No cubemap to upload |
| 5 — De Kasteeltoren (`lvl04a`) | Two 128 x 128 and four 256 x 256 faces, as detailed above | **Yes** |

[`normalizeSkyboxFaces()`](../src/skybox.js) now runs before cubemap creation.
It chooses the largest source dimension, capped by the GPU's maximum cubemap
size, and makes every face that common square size. For the shipped campaign
this is **256 x 256**. Only images that need resizing are copied, with smooth
full-image scaling. Matching images are reused directly; repeated references
to a resized image share one canvas. This creates two resized images in Het
Kasteel and one in the Tower, once during level loading, with no per-frame work.

Face order, orientation, sRGB interpretation and missing-face fallback remain
unchanged. The source PNGs are untouched. Forest and Graveyard sky images need
no conversion; the Caves retain their existing background. The shadow browser
fixture now renders the normal skybox, with its neutral-background workaround
removed.

Focused verification commands:

- `node --test tests/skybox.test.mjs`: actual campaign artwork dimensions,
  shared resized faces, unchanged compatible images, GPU size limits and loaded
  image validation.
- `node tests/skybox-scenes.mjs`: cubemap GPU uploads and six-direction artwork
  checks, plus the real Tower loader/rendering path.

All four unit checks passed. The browser check covered **24 sky views** (six
directions in each of the four levels with skyboxes), with artwork/orientation
pixel differences no greater than one 8-bit channel step and zero GL errors.
Three normal Tower room views also rendered with the actual skybox and no GL
errors. The Caves configuration was confirmed to have no authored cubemap.
Only these skybox checks were run; previous gameplay suites were not rerun.
The [rendering report](../current_work/skybox-dimensions-2026-10-05/scenes-1791222355164/report.json)
and captured sky views are retained.

The campaign audit is retained in
[`current_work/skybox-dimensions-2026-10-05/`](../current_work/skybox-dimensions-2026-10-05/).
No build or package is generated by this fix.
